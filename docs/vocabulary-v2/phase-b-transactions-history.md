# Phase B transaction and History contract

## Storage layout and identities

Vocabulary data is rooted at `00_Archive/21_VocabularyData/`. Canonical vocabulary stores and their manifests remain the domain services' responsibility. Coordinator-owned transient data is local to the device at `transactions/<deviceId>/<sessionId>/`; finalized, immutable History batches are stored separately at `history/<deviceId>/<sha256(batchId)>.json`. Device and session identifiers used as path segments are restricted to ASCII letters, digits, `_`, and `-`.

Every canonical write records a base and result identity. A new absent file has base revision `0` and `expectedHash: null`; an existing revision-0 file is distinct and must carry its verified `sha256-v1:<hex>` hash. A write's top-level result revision is exactly base revision plus one. History stores the same base/result revision and hash pair per `(storeId, path)`, including unchanged canonical files when a batch depends on them. Canonical JSON uses sorted object keys, and hashes use the `sha256-v1:` prefix.

History records field-level changes, not whole-store snapshots. A batch contains its local device and transaction IDs, affected store paths, entities, and before/after presence and values. Registered store handlers resolve fields against domain identity and construct restore plans; restore rejects an unregistered store. The default resolver handles V2 records by looking up `record.key`, never by array position. Protected identity fields are only admitted as part of a complete, explicit `entityCreate` or `entityDelete` lifecycle. Restore defaults to clean changes, reports already-restored changes, and requires explicit change IDs to overwrite conflicts. Entity lifecycle groups are all-or-nothing. A successful restore writes a new inverse History batch, so the same mechanism supports redo.

Review actions are first recorded in bounded local journal segments. Ordinary checkpoints install canonical Review data and an updated summary in one pending transaction; they do not create permanent History. Closing a changed Review session records one final History batch for that session. A net-zero session creates no History batch. Undo and redo each create their own inverse batch.

## Pending transactions, locks, and recovery

The coordinator keeps in-process path locks in a shared `WeakMap` keyed by the adapter object, sorts paths before acquiring locks, and preflights every participating store before installing any mutation. This coordinates coordinator instances sharing one adapter in the same JavaScript runtime. It is not a distributed lock, and it does not provide storage-level compare-and-swap across processes or devices. The host `DataAdapter` offers no multi-file atomic transaction, so the coordinator writes a verified pending intent before installation and uses staged files plus verified backups while replacing canonical files.

Recovery scans only `transactions/<this-device>/`. It replays local pending intents only when each target is still in its recorded base or result state. A third state is preserved, the pending intent remains, and the relevant store is reported as conflicted. A foreign device's pending work is not inspected, replayed, deleted, or merged. A malformed local intent with a safely validated store/path scope blocks that scope; an intent with no trustworthy scope remains diagnostic and does not block unrelated stores.

The pending intent contains the complete mutation payload, preconditions, and result conditions. Recovery treats a target already at the result identity as installed and a target still at the base identity as eligible for installation. It verifies writes before cleanup, retains tx-owned evidence when recovery cannot prove the expected state, and never garbage-collects canonical user or shard files. Review finalization installs and verifies the History write before deleting its journal and summary files. The in-memory fault test injects a crash before the History install, verifies the journal, summary, and intent remain, then verifies recovery completes the History write before cleaning those files.

These guarantees provide recoverable local transactions, not distributed atomicity. An external writer can race between an adapter read and rename because the adapter has no CAS primitive. Cross-store domain references are represented as coordinator preconditions so their expected store identities are checked again under the same in-process path locks as the mutation. `VocabularyHistory.restore` validates and aggregates preconditions from all store planners, deduplicates identical identities for one path, rejects conflicting identities for one path, and forwards the result to the coordinator. It rejects a precondition that overlaps a planned write because that write already carries its own base identity.

The V2 core service pairs `getFamilyEvidence(surface)` with the loaded canonical snapshot identity, and Context save passes that identity as a core precondition. The core History planner also returns Context and Review manifest/shard identities checked while validating a family removal. The real coordinator Context regression changes or deletes the core family after evidence is read but before commit; both cases return a scoped conflict and install no Context files. History tests separately mutate a dependency after planning and confirm the canonical restore conflicts without writing, and verify that two different expected identities for one path return a conflict rather than selecting one. These checks close the identified in-process race paths; they do not turn the adapter into a cross-process CAS or distributed transaction system.

## Review journal and summary bounds

When `DataAdapter.append` exists, the coordinator writes sequenced, canonical JSONL action envelopes to `review-000000.jsonl` and subsequent segments. Each complete newline-terminated row has its own canonical SHA-256 integrity hash, and each segment is bounded to 64 KiB. Review supplies the expected next sequence; under the session lock, the coordinator resolves exact action-ID retries first and rejects a stale sequence before writing anything. An action is ACKed only after readback verifies its sequence, ID, payload, and hash. A final non-newline suffix is retained as recovery evidence and is not reported as an action; retry writes the same next sequence in a fresh segment. A malformed complete row or oversized segment fails closed. Before finalization, a damaged active segment is copied and byte-verified under a non-active `.evidence-<hash>` name, then the active journal is removed in the transaction only after canonical writes and final History are verified. This keeps recovery evidence without causing a later runtime to replay a finalized session. When the adapter has no append operation, the coordinator retains the compatible packed `review-000000.segment.json` format and uses a verified stage/backup replacement of the current bounded segment. A 100-action regression checks the native path appends exactly one action line per call without rewriting prefixes, while the fallback regression verifies its crash-recoverable rewrite behavior.

Pending summaries are also segmented into files no larger than 64 KiB, with a 16 MiB total payload limit. Each summary manifest has a monotonically increasing generation and `flushedThroughSequence`; individual segment files use revision `1` and carry the manifest generation separately. A checkpoint can advance the sequence only in the same transaction as canonical writes. Old summary segments are deleted in that checkpoint transaction after result verification. Finalization removes journal and summary evidence only after canonical result conditions and History have been verified.

Coverage includes existing versus absent revision zero, multi-store preflight, shared in-process locks, base/result/third-state recovery, foreign pending isolation, native bounded JSONL appends and torn-suffix recovery, incomplete first-row retry, complete-row integrity failure, expected-sequence stale-writer rejection, same-session concurrent Review writers, finalization and new-runtime recovery from non-active evidence, packed-segment fallback replacement, repeated summary checkpoints, Review restart/replay, final History persistence, full entity enrollment undo/redo, an injected pre-History-install failure followed by successful local recovery, and Context/core reference precondition races for deletion and replacement.
