# Phase B: Context, Review, and durable session state

This document records the current contracts and focused evidence for Context and Review. It is not a Phase B acceptance report: the complete Phase B gate, host/UI integration, and remaining interoperability checks are separate work.

## Context contract

`createVocabularyContextService({ transaction, vocabularyService, verifySource, now, maxRecords, maxBytes })` exposes `saveContext`, `getContext`, `listFamily`, `verifySource`, and `load`. It uses vocabulary family resolution; it does not parse PDFs, search PDF text, or reconstruct an Anchor from coordinates.

Before saving, Context calls `vocabularyService.getFamilyEvidence(surface)`. That API returns the family and the identity of the same loaded vocabulary snapshot from one serialized service turn. A missing family or missing canonical snapshot is rejected. The Context commit carries the core store ID, path, revision, and hash as a transaction precondition. If that core snapshot changes or disappears between family resolution and Context commit, the coordinator returns a scoped conflict and installs no Context shard or manifest.

The Context ID is derived only from `(familyKey, documentId, anchorId)`. The stored record also retains and validates the complete Anchor/source tuple, including route key, source fingerprint, page identity, page number hint, quote and text position. Saving an already-used tuple returns the existing record without writing; a changed sentence is reported with `requiresUserEdit: true` rather than creating a duplicate. `listFamily` uses stable cursor pagination. `verifySource` checks the saved Anchor against the injected current-source verifier. A verifier must return `status: "verified"`, `sourceCurrent: true`, `pageCurrent: true`, and the identical Anchor. An Anchor-store-only lookup is insufficient to prove the current route and page.

The host verifier factory is `createContextSourceVerifier` in `plugin/vocabulary/context-source.cjs`. It checks the current document route, existing Anchor, source identity and already-verified page evidence. It does not open or scan the PDF. Production runtime wiring must provide that verifier; the runtime's fail-closed default intentionally cannot save Context.

Context data lives under `00_Archive/21_VocabularyData/contexts/`, with `manifest.json` and fixed-prefix `<hex-prefix>.json` shards. The store ID is `vocabulary-contexts-v1`, and the record kind is `context`.

## Review contract

`createVocabularyReviewService({ transaction, vocabularyService, now, makeId, setTimeout, clearTimeout, flushEvery, idleMs })` exposes `openSession`, `getState`, `listDue`, `enroll`, `unenroll`, `remember`, `forget`, `skip`, `flush`, `close`, and `getStatus`. It validates each persisted Review state and checks that its `familyKey` still resolves in the vocabulary store. Due queues are ordered by UTC due instant and family key and use cursor pagination.

The fixed intervals are `[1, 3, 7, 14, 30]` days. Enroll creates box 1 due immediately. Remember advances by one box, capped at box 5, and schedules the interval for the new box. Forget returns to box 1, schedules one day, and increments both `reviewCount` and `lapseCount`. Times are canonical UTC ISO instants. Known families (status 5) are filtered without changing Review state; `skip` returns with zero writes. `unenroll` preserves the learning state and only suspends enrollment.

Canonical Review state lives under `00_Archive/21_VocabularyData/review/states/`, with `manifest.json` and adaptive shards. Its store ID is `vocabulary-review-v1`; its kind is `review-state`; the stable record ID is the family key.

## Shards and partial reads

Both stores use `createShardedStore` and the same deterministic partitioner. Records are assigned by the lowercase SHA-256 digest of their stable ID. Prefixes start at one hex character and split recursively until every canonical shard envelope has at most 512 records and 256 KiB of UTF-8 JSON. A single record that cannot fit is rejected as `VOCAB_SHARD_RECORD_TOO_LARGE`; it is never truncated. Prefixes and manifest entries are sorted deterministically. The manifest is the sole active-shard set. A write changes only affected shard files and the manifest; unchanged data is a zero-write no-op. Fixed prefix paths are reused, and files omitted from the active manifest remain inert rather than being deleted.

Reads validate the canonical manifest, every referenced shard's path/revision/hash/byte count/record count, record IDs and prefix membership, and exact correspondence between loaded shards and active references. A manifest that names a missing shard fails closed with `VOCAB_SHARD_MISSING`; it does not return an empty store. When the manifest is absent, `readShardedStore` requires an injected `hasShardFiles(root)` probe. `createShardedStore` supplies a production probe backed by the DataAdapter's `exists(root)` and `list(root)`: any immediate file named as a lowercase SHA-256 prefix shard causes `VOCAB_SHARD_MANIFEST_MISSING`. The same rule covers a remote shard that arrived first, a deleted manifest, and a partial JSON shard. An absent directory or a genuinely empty directory is still an empty store. Missing list support, an invalid listing, or a listing error fails closed rather than assuming empty. Tests cover the first-shard-before-manifest case, manifest deletion and blocked replacement planning, absent/empty directories, and malformed shard JSON.

Context additionally validates each loaded record's schema, full identity, stable ID and family/surface relationship. Review additionally validates its state fields and vocabulary-family references. The Review History resolver and restore planner use the same active-manifest reader and orphan-shard probe. A malformed record or missing vocabulary family is surfaced as an error, not silently omitted.

## Review journal, checkpoint, and final History

Review actions are appended through the coordinator API `appendJournalAction({ sessionId, actionId, payload })`. When the host adapter exposes native `append`, the coordinator writes one canonical, integrity-hashed JSONL row per action under `transactions/<deviceId>/<sessionId>/review-000000.jsonl` and subsequent segments. Each segment is bounded at 64 KiB; the session has a 10,000-action limit. A stable action ID is idempotent only for the same payload. The coordinator reads back and verifies the ACKed sequence, ID, payload and hash before Review advances its working state and returns `committed`. An interrupted final line without a newline remains unacknowledged recovery evidence; a complete invalid row fails closed. Before finalization, damaged raw bytes are copied and verified under a non-active `.evidence-<hash>` name so the active journal can be removed only after canonical writes and History verify, without replaying a completed session. For adapters without native append, the coordinator keeps the packed `review-000000.segment.json` format and uses a verified stage/backup rewrite of only the current 64 KiB segment.

Review defaults to a checkpoint after 20 unflushed actions or 5 seconds idle; explicit `flush()` and `close()` also checkpoint. The service accepts threshold overrides for tests, while the runtime uses these defaults. A checkpoint writes changed canonical Review shards/manifest and a new pending summary in the same verified WAL transaction. Only that transaction may advance `flushedThroughSequence`. The summary manifest is `transactions/<deviceId>/<sessionId>/summary.pending.json`; its `summary-<generation>-<index>.segment.json` chunks are each at most 64 KiB, with a 16 MiB aggregate limit. The summary carries bounded Review before/after state and store revision/hash baselines, not vocabulary or Context contents. Ordinary checkpoints retain the journal and pending summary.

On close, Review folds all actions since the session baseline into at most one `review-final:<sessionId>` History batch. Intermediate checkpoints do not create permanent History. A net-zero close creates no History batch but verifies the canonical snapshots before removing local journal/summary evidence. For a changed session, journal and summary cleanup happens only after canonical state and final History are verified. A failed finalization preserves its evidence for local recovery. History stores immutable batches under `00_Archive/21_VocabularyData/history/<deviceId>/<sha256(batchId)>.json`; restore is handler-based, field-level, clean-only by default, and requires explicit change IDs to overwrite conflicts. New-record enroll/undo/redo is an all-or-nothing entity lifecycle.

The coordinator uses sorted in-process path locks shared by coordinator instances for one adapter, all-store preflight, a verified pending intent, staged replacements and readback before acknowledgement. Recovery inspects only the local device's pending work. It ignores foreign-device pending files and preserves a third-state conflict with its evidence. These are recoverable local transactions, not distributed atomicity or cross-device merging; a `DataAdapter` has no compare-and-swap primitive.

## Cross-store family references and restore limits

`createVocabularyRuntime` serializes its own Context save, Review operations and History restore. When a core restore removes the last member of a family, its reference validator reads the Context and Review manifests plus every active shard, rejects a still-referenced family, and returns the checked snapshots as transaction preconditions. Context save independently preconditions the exact vocabulary snapshot used to resolve its family. This closes the tested interleaving where a family is deleted or replaced after Context family lookup but before Context commit. Root also verified both directions of the two-runtime interleaving in `tests/vocabulary-v2-runtime.test.mjs` (4/4 cases). Separate runtimes still rely on coordinator preconditions rather than a shared process lock.

Review History restore resolves current Review state from the active manifest/shards and verifies its family still exists. It fails closed if the vocabulary family is missing; re-creating a missing family solely to satisfy an old Review batch is not implemented. Context has no separate History restore handler yet. The exact behavior for restoring a core family while historical Context or Review references exist remains constrained by current reference checks; it does not silently recreate or rebind those references. Directory enumeration detects present orphan shard paths when the manifest is absent, but it cannot detect a shard that has not arrived yet or provide a distributed snapshot across a live sync.

## Focused verification

After the Context core-snapshot precondition and manifest-absence detection tests were added, this focused command passed 55 tests with zero failures or skips:

```sh
node --test tests/vocabulary-review-service.test.mjs tests/vocabulary-context-service.test.mjs tests/vocabulary-sharded-store.test.mjs tests/vocabulary-history.test.mjs tests/vocabulary-transactions.test.mjs tests/vocabulary-review-transaction-integration.test.mjs tests/vocabulary-v2-runtime.test.mjs
```

The Context race cases use a real `VocabularyTransactionCoordinator` and `VocabularyService`; the test injects deletion or replacement of the core bytes immediately before coordinator commit, then asserts a vocabulary-store conflict and no Context files. Orphan-shard tests also confirm Context save, Review session open, and Review History resolution fail closed when a manifest is absent. The command includes in-memory adapter fault/recovery, Review restart/checkpoint/finalization, History lifecycle undo/redo, shard boundary and partial-sync cases, and both directions of the two-runtime Context/core-restore interleaving. These are focused contract checks, not the complete Phase B Fast/Browser/Race gate, not host/UI validation, and not device acceptance. No skipped or weakened case is used as evidence of completion.
