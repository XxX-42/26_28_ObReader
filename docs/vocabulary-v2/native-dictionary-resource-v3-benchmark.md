# Native resource-v3 dictionary benchmark handoff

Prepared only; Native execution, deployment, process restart and startup measurement are **NOT_RUN**. Existing `dictionary-resource-benchmark` and `dictionary-v3-comparison-benchmark` are localhost Chrome harnesses; neither proves Native performance. The requested `scripts/benchmark-dictionary-resource-v3.mjs` and `directDictionary` seam do not exist at base 174858b. This harness reuses the existing comparison instrumentation loader and actual VocabularyDictionary class without changing production code.

After the coordinator releases full gates and grants exclusive Native time, and separately stages verified resources through the authorized deployment workflow, run from the repository with dependencies installed:

```sh
OBREADER_NATIVE_DICTIONARY_LEASE=exclusive-after-native-gates node tests/native-dictionary-resource-v3-benchmark.mjs --run http://127.0.0.1:49786 /Users/jiajia/Documents/ObReader-Apple-Test /absolute/outside-vault/native-dictionary.json
```

Windows coordinator substitutes its verified existing CDP URL, exact DataAdapter basePath and outside-Vault output path. Output parent must exist; the file is reserved exclusively before connection. Do not run against a locked Mac session, during Native UI acceptance, or without a coordinator lease. This script attaches to an existing target; it cannot launch, unlock, enable the plugin, create Readers, install resources or change learning data.

The harness requires one exact app://obsidian.md/index.html target with matching real adapter.basePath and zero Readers through both active.views and workspace.getLeavesOfType('pdf-web-reader-view'). The pdf-web-reader plugin must already be disabled (neither loaded instance nor enabledPlugins membership), preventing its startup/cache background Worker from contaminating lookup timings; the harness refuses rather than changing plugin state. The benchmark bundle remains in a lexical IIFE scope exposed only through a disposable CDP handle, so an existing NativeDictionaryBenchmarkRuntime global is never overwritten and no benchmark global remains. The handle is disposed after success or failure. It bundles only repository test/runtime source in Node, then passes every resource read through real app.vault.adapter.read/readBinary in the Native renderer. No Node filesystem access reads Vault/runtime data. DataAdapter writes are unavailable to the wrapper; binary writes are structurally zero. A v2 fallback fails the trial. Each trial gets an isolated disposable IndexedDB name, leaving asynchronous work and old generations in the real namespace untouched. This does not test stale-generation migration behavior.

Five declared trials each construct a fresh Dictionary instance/Worker, measure its first real v3 `zyzzyva` lookup, then 20 same-key repeats. These are instance-cold trials in an existing Native origin/process; they are **not** process-cold, fresh-origin or distinct-key working-set evidence. Native OS file caches are retained. No retry or hidden key prewarm occurs. Repeat samples classify measured resident hits against miss and real binary-read deltas. All 100 repeat samples remain in raw output. Errors retain prior completed trials and stop the run; absent trials remain NOT_RUN by implication, never count as passes.

Recorded metrics include real adapter class/Vault/app URL, read and readBinary paths/bytes/elapsed I/O, first lookup and repeat durations, cache hits/misses, Worker-reported decode CPU duration, and decodeBlock wall duration. The latter includes Worker startup/transfer/scheduling and may include fallback; workerPresent plus Worker metrics must be inspected before calling it Worker evidence. It is not total Worker CPU. The manifest synchronous call duration measures only invocation until its first async suspension. Total async manifest elapsed time includes I/O and CPU and **must not be called blocking**.

Startup added blocking is explicitly **NOT_MEASURED**. The attached runtime starts after application startup, so neither its constructor nor manifest elapsed time can establish production startup impact. Minimum reliable follow-up: use the authorized Native startup workflow with a temporary test-only bundle that places performance marks around production startup constructor invocation and around JSON.parse/validateManifest plus every synchronous verifyManifestIndex segment (separate asynchronous crypto/I/O waits). Capture a renderer CPU trace before plugin load and pair five matched baseline/candidate startups on the same Native process policy; report synchronous task durations and their summed incremental contribution separately from end-to-end startup wall time. Until that controlled capture exists, leave the <50ms startup acceptance gate undecided. Do not infer it from long-task absence or localhost Chrome measurements.

Validation performed here: `node --check tests/native-dictionary-resource-v3-benchmark.mjs` only. No Native, browser, resource read, benchmark, heavy gate or Vault operation was executed.
